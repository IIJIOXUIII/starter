# ADR-002: BFF вместо отдельного API Gateway на старте

- Статус: принято (M0)
- Дата: 2026-11-22

## Контекст

Браузер — первый клиент платформы. Микросервисная архитектура традиционно
предполагает API Gateway, но для браузерного клиента есть BFF-паттерн.

## Решение

- Роль «шлюза для браузера» выполняет **Nuxt BFF** (server routes Nitro):
  агрегация сервисов, сессии/cookies, маппинг ошибок, валидация входа.
- Edge-задачи (TLS, роутинг, rate limit, security headers) — **Traefik**.
- Сервисы **не выставляются наружу**; каждый валидирует JWT самостоятельно
  (JWKS от auth-service) — defense in depth.
- Выделенный Go API Gateway появится, когда придут внешние клиенты
  (мобильное приложение, партнёрский API).

## Альтернативы

- **Kong/Traefik Hub/собственный gateway с первого дня** — лишний хоп
  BFF→Gateway→сервис, дублирование агрегации и сессий, дополнительный код
  без потребителя на старте.

## Последствия

- Меньше инфраструктуры и задержки на старте.
- Часть обязанностей шлюза (rate limit) дублируется на BFF до появления gateway.
- Добавление gateway в будущем не требует изменений в сервисах (они уже
  stateless и валидируют JWT сами).
